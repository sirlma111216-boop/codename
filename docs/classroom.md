# 학급 모드 (클래스와 학생 방장)

`03-claude-code-classroom-addendum.md` 의 구현 설명서. 게임 규칙·원본 콘텐츠 처리·일러스트·로그인 없는 참가는 기존 명세 그대로이며, 바뀐 것은 **수업 운영과 참가자 배치 구조**다.

## 1. 흐름

```
교사: 클래스 만들기(이름·정원) ─► 초대 링크·QR 공유
학생: 링크 열기 → 닉네임 → 클래스 대기실
교사: 학생 목록에서 ‘방장 지정’
방장: 게임방 만들기(이름·정원 4~8, 방장도 좌석 1개)
학생: 방 목록에서 ‘참가 신청’ (좌석을 차지하지 않음, 미결 신청은 한 방만)
방장: 승인/거절 (정원 안에서만, 승인 뒤에만 좌석 확정)
학생: ‘입장하기’ (방이 명단 반영을 확인한 뒤에만 켜짐)
방 안: 팀·역할 고르기 → ‘준비 완료’
방장: ‘게임 시작’ — 정원 충족·전원 접속·전원 준비·역할 조건·팀 차이 ≤1 일 때만, 이 순간 명단 잠금
각 방 독립 진행 → 결과 → 같은 구성으로 재경기(역할 다시 고르기) 또는 클래스로
교사: 수업 종료 → 진행 중 게임은 ‘수업 종료로 중단’(승패 없음), 방 정리
```

교사가 모든 방을 대신 만들거나 아무 학생이나 방을 만드는 방식이 아니다. 독립 게임방(초대 링크)은 그대로 남아 있지만 학급 방과 분리되어 있다.

## 2. 인원 (운영 설정 — 원작 인원 규정이 아니다)

원작 기본판의 인원 표기는 4–8+ 이며 8명이 상한이라는 뜻이 아니다 ([CGE](https://www.czechgames.com/games/codenames)). 아래는 이 앱의 운영 설정이다.

| 항목 | 기본 | 설정 위치 |
|---|---|---|
| 클래스 학생 정원 (교사 제외) | 40 | 교사 화면 ‘수업 설정’ |
| 클래스 정원 상한 | 60 | `wrangler.jsonc` `CLASS_MAX_STUDENTS` |
| 클래스당 게임방 한도 | 15 (60명을 4인 방으로 모두 편성 가능) | `CLASS_MAX_ROOMS` |
| 방 정원 | 기본 6, 교사가 4~8 안에서 범위 지정 | 교사 화면 ‘수업 설정’ |
| 규칙 | 표준 대전만. 4명 미만 방을 소인원 변형으로 바꾸지 않는다 (소인원 변형은 독립 방에 남아 있다) | — |

한 방은 늘 두 팀이다. 5·7명 방은 3:2·4:3 처럼 차이 1명 이하로 나누며, 방장 화면의 ‘팀 고르게 나누기’가 이를 돕는다. 배치 예시(24명 → 6명×4방, 30명 → 6명×5방, 32명 → 8명×4방)는 교사 화면에 **운영 예시**로만 보인다.

## 3. 역할과 권한

| 역할 | 할 수 있는 것 | 서버 검사 위치 |
|---|---|---|
| 교사 (클래스 관리자) | 방장 지정·해제, 학생·방 현황, 입장 잠금, 초대 갱신, 대기 중 학생 이동, 방 관리권 재지정, 방 닫기, 공지, 도움 요청 확인, 강퇴, 자리 재지정, 수업 종료, 방 **공개** 관전 | `class-logic.ts` `applyClassCommand` |
| 학생 방장 | 자기 방 만들기·정원 변경, 신청 승인·거절, 대기 중 내보내기, 방 닫기(게임 중 제외), 팀 고르게 나누기, 게임 시작·재경기 | 클래스: 방의 `hostMemberId` / 방: `room.hostId` (클래스가 반영) |
| 학생 참가자 | 신청·취소, 방 나가기(게임 중 제외), 팀·역할 선택, 준비, 도움 요청 | 클래스·방 각각 |
| 스파이마스터/추측자 | 기존 원본 규칙의 게임 행동 | `engine.ts` |

- 방장이 자동으로 스파이마스터가 되지 않는다. 방장·교사라는 이유로 정답을 받지 않는다 (교사 관전은 추측자·관전자와 같은 공개 projection).
- 방장 지정을 해제해도 방은 지우지 않는다. 그 방의 관리권만 거둬지고(방에도 반영되어 옛 방장의 명령은 거절), 교사가 다른 참가자에게 넘기거나 방을 닫는다.
- 교사 부재로 교사 권한을 학생에게 자동 승격하지 않는다. 교사는 같은 브라우저 세션으로 돌아오거나, 클래스를 만들 때 **한 번만** 보여 주는 복구 키로 다른 기기에서 이어서 관리한다. 복구 키는 초대 링크와 별개이며 서버에는 SHA-256 해시만 저장한다.
- 교사가 학생 방에 플레이어로 참여하는 기능은 첫 학급 모드에 없다.

## 4. Cloudflare 구조

```
브라우저 ─┬─ /api/classes/{classId}/ws ─► ClassroomDurableObject (클래스 1개)
          │                                  membership · 교사/방장 권한 · 방 메타데이터 · 신청 · 좌석 · revision
          └─ /api/rooms/{roomId}/ws ─────► GameRoomDurableObject (방 1개)
                                             보드 · 비밀 키 · 턴 · 역할 · 게임 기록
     ClassroomDO ──classSync(버전 붙은 전체 명단)──► GameRoomDO
     GameRoomDO ──lockForStart / confirmStart / cancelStart / releaseRoster / report(공개 요약)──► ClassroomDO
```

- 외부 DB 서비스 없음. 두 객체 모두 SQLite-backed Durable Object 내장 저장소 + Hibernation API + 재접속 snapshot.
- `wrangler.jsonc` migration `v2`: 기존 방 클래스 이름만 `RoomDurableObject → GameRoomDurableObject` 로 바꾸고(저장된 방 유지) `ClassroomDurableObject` 를 추가.
- **학생은 클래스 소켓 1 + 자기 방 소켓 1** 만 연다(게임 중에도 교사 공지는 클래스 소켓으로 받는다). 모든 방을 구독하지 않는다. 교사는 클래스 소켓 + 관전하려고 연 방만.
- 클래스 화면에는 방의 공개 요약(단계, 차례, 남은 요원 수, 힌트 개수, 결과)만 있다. 단어판·정답·keyId·seed·힌트 초안·방 안 토론은 없다. 학생은 다른 방의 명단·신청도 받지 않는다.
- 방 id 를 알아도 다른 클래스 학생은 상태 조회·소켓 구독·참가·관리가 모두 거절된다(방은 클래스가 보낸 명단의 세션만 받는다). 학급 방은 독립 방의 초대 경로로 들어올 수 없다(`classManaged`).
- 내부 RPC 는 Worker 가 쿠키로 계산한 세션 해시만 넘기고, 클라이언트가 보낸 값을 믿지 않는다.

## 5. 배정의 일관성 (DO 사이에 단일 트랜잭션이 없으므로)

**좌석 배정의 최종 판단은 클래스 객체 한 곳에서 한다.** 게임방에는 좌석을 더하는 경로가 없다.

1. **예약을 먼저 저장** — 승인·이동·방 만들기는 클래스가 상태를 저장한 뒤 응답한다. 방의 `syncVersion` 이 오른다.
2. **멱등 반영** — 클래스가 방에 전체 명단을 버전과 함께 보낸다(`classSync`). 방은 더 새 버전만 적용하므로 재전송·순서 바뀜에 안전하다.
3. **확인 뒤 입장 안내** — 방이 확인하면 `syncedVersion` 을 올리고, 그때 학생 화면의 ‘입장하기’가 켜진다.
4. **실패하면 재시도** — 반영이 실패하면 좌석은 예약된 채로 두고(다른 학생에게 넘기지 않음) alarm 이 지수 백오프로 다시 보낸다.
5. **opId 멱등** — 모든 클래스 명령에 opId 가 붙고, 같은 opId 재전송은 이전 결과만 돌려준다(방 만들기 재전송으로 방이 두 개 생기지 않는다).
6. **명단 버전 검사** — 승인·내보내기·정원 변경은 `expectedRosterVersion` 을 붙인다. 마지막 한 자리에 두 승인이 같이 오면 하나만 성공한다.
7. **시작 잠금** — 방장이 시작하면 방이 먼저 조건을 검사하고, 클래스에 `lockForStart(방이 본 명단 버전)` 를 요청한다. 클래스는 그 버전이 최신이고 반영이 끝났고 정원이 찼을 때만 잠근다. 잠긴 동안 승인·이동·신청·나가기는 모두 거절된다. 방은 게임을 저장한 뒤 `confirmStart`, 실패하면 `cancelStart`. 방이 확인을 못 보내면 클래스가 20초 뒤 방의 실제 상태를 물어(`statusForClass`) 잠금을 확정하거나 푼다. 방의 시작 처리는 `blockConcurrencyWhile` 안에서 해 그 사이 다른 명령·명단 반영이 끼어들지 못한다.
8. **잠금 해제** — 게임이 끝나고 방장이 대기실로 돌아가면 방이 `releaseRoster` 를 보낸다(실패하면 alarm 재시도).
9. **관리권·권한 취소 반영** — 방장 교체·지정 해제·강퇴·교사 세션 추가는 명단 버전을 올려 방에 반영하고, 방은 반영된 방장만 관리 명령을 받는다.

## 6. 연결 끊김·이동·종료

- 연결 끊김과 자진 퇴장을 구분한다. 끊긴 학생의 좌석은 그대로이고, 다시 접속하면 원래 방·팀·역할로 돌아온다. 정답을 본 학생의 추측자 전환 제한은 그대로다.
- 대기 중 이동(교사)은 기존 좌석 해제와 새 좌석 확보를 같은 저장에서 처리하고 두 방 모두 다시 반영(준비 초기화)한다.
- 게임이 시작되면 명단이 잠긴다. 지각생은 클래스 대기실에서 다음 게임을 기다린다.
- 방장이 끊겨도 게임은 계속된다. 교사가 같은 방 참가자에게 관리권만 넘길 수 있다(역할·정답 접근권은 그대로).
- 진행 중 강퇴는 역할을 자동 재배치하지 않는다(연결만 끊고 자리는 남김). 참여가 불가능하면 기존 스파이마스터 교체 정책이나 게임 중단을 쓴다.
- 수업 종료는 교사가 확인한 뒤 실행한다. 진행 중 게임은 ‘수업 종료로 중단’으로 기록하고 승패를 만들지 않는다. 교사는 끝난 뒤에도 기록을 읽기 전용으로 본다.

## 7. 수명과 정리

- 활성 수업의 방은 방 자체 TTL 로 지우지 않는다. 학급 방은 오래 조용하면(6시간) 먼저 클래스에 `roomAlive` 를 묻고, 클래스가 쓰지 않는다고 할 때만 정리한다.
- 수업이 끝나거나(교사) 24시간(`ROOM_TTL_HOURS`) 활동이 없으면 클래스가 모든 방을 닫고 정리 목록에 올린다. alarm 이 방마다 `purgeForClass` 를 부르고, 실패하면 다음 alarm 에서 이어간다. 정리된 방은 늦게 도착한 명단 반영으로 되살아나지 않도록 짧은 묘비를 3일 남긴다.
- 정리가 끝난 클래스는 보존 기간 뒤 저장소까지 비운다.

### 한계 (실측하지 않은 것)

- **60명 지원은 이 앱의 봇 시뮬레이션으로 측정한 범위다.** 봇은 실제 브라우저와 같은 경로(쿠키 세션·HTTP·WebSocket)를 쓰지만 한 대의 PC에서 돌렸고, 실제 학교 와이파이·휴대폰 60대·브라우저 렌더링 부하는 재현하지 않았다. 60명을 넘는 인원은 검증하지 않았다.
- 게임 행동 검증(힌트 제출·카드 공개·경쟁)과 단순 연결 부하(동시 소켓 수)를 구분해 보고한다. 봇의 추측은 무작위라 실제 수업보다 빨리 끝난다.
- Cloudflare 무료 한도(Durable Object 요청 하루 100,000건 등)를 넘는 규모는 시험하지 않았다. 무료 운영을 보장하지 않는다.
- 학급 기능의 검증 성공은 한국어 정식판 원본 콘텐츠 확보와 무관하다. 정식 콘텐츠는 여전히 미확보다([content-status.md](content-status.md)).
